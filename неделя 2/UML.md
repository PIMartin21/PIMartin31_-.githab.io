#### 1.1. Диаграмма вариантов использования

В техническом задании предусмотрена возможность управления гардеробом,
подбора образов и просмотра аналитики.

В ранее подготовленной диаграмме вариантов использования присутствуют
сценарии:

- добавление вещи в гардероб;
- просмотр и редактирование вещи;
- удаление вещи;
- просмотр списка вещей с фильтрацией по категориям;
- генерация образа по событию (свидание, работа, спорт, прогулка);
- подбор сочетаний для вещи;
- сохранение образа;
- просмотр статистики;
- напоминания о редко используемых вещах;
- формирование списка покупок;
- финансовый учёт.

После проверки установлено, что не все сценарии соответствуют актуальной
версии технического задания. В результате актуализации ТЗ из проекта
исключены:

- генерация образа по событию (свидание, работа, спорт, прогулка);
- подбор сочетаний для вещи;
- напоминания о редко используемых вещах (push-уведомления);
- формирование списка покупок;
- финансовый учёт.

Вместо них в диаграмму вариантов использования добавлены сценарии:

- подбор образа по погоде;
- ручной подбор образа;
- отображение списка «забытых» вещей (не использовались более 30 дней);
- показ вещей той же категории.

Остальные сценарии соответствуют актуальной версии технического задания.

#### 1.2. Диаграмма компонентов

На диаграмме компонентов отражена физическая структура приложения
SmartWardrobe. Основные компоненты:

- **Модуль персональный кабинет и панель управления** — интерфейс пользователя;
- **Локальный контроллер (бизнес-логика)** — обработка действий пользователя;
- **SQLite (локальное хранилище)** — хранение данных гардероба и образов;
- **Подсистема «Управление гардеробом»** — добавление, просмотр,
  редактирование вещей;
- **Подсистема «Подбор образов»** — подбор по погоде, ручной сбор,
  сохранение образов;
- **Подсистема «Аналитика и советы»** — расчёт статистики и список
  забытых вещей;
- **OpenWeather API** — внешний источник данных о погоде.

После проверки диаграммы компонентов на соответствие актуальной версии
технического задания внесены следующие изменения:

| Что | Действие | Причина |
|---|---|---|
| Блок cloud services | Удалён | Убрано облачное резервное копирование |
| Формирование списка покупок | Удалён | Убрано из ТЗ |
| Сочетание вещей | переименован | Заменено на «показ вещей той же категории» |
| Генератор по погоде/событию | Переименован | Оставлен только подбор по погоде, без событий |
| Сохранение образа | Добавлен | Есть в актуальном ТЗ |
| Ручной подбор образа | Добавлен | Есть в актуальном ТЗ |

После внесённых изменений диаграмма компонентов соответствует
актуальной версии технического задания.

### 2. Декомпозиция функциональности на задачи разработки

После проверки UML-диаграмм требование декомпозируется на задачи
разработки:

1. Реализовать гардероб с возможностью добавления в него вещей.
2. Реализовать возможность создания подгардероба.
3. Реализовать просмотр вещи с возможностью изменения данных о ней.
4. Реализовать отслеживание последнего использования вещи.
5. Реализовать список забытых вещей.
6. Реализовать подбор образов по погоде.
7. Реализовать ручной сбор образов.
8. Реализовать сохранение образа.

Таким образом, требование технического задания сопоставляется
с соответствующими UML-диаграммами и переводится в конкретные
задачи реализации.
